Padma: business systems without writing code

How we built an in-house no-code platform at Genuine Technology for building enterprise systems like HR, payroll and ERP: drag-and-drop pages saved as data, forms that create their own database tables, and pages that can be embedded, called as APIs or sent out as surveys.

Role
Programmer, core platform team (Genuine Technology)
Period
2021 – 2023
My part
Data handlers · data binders · entity builders · charts · embedding
Stack
.NET Core (C#) · ASP.NET MVC · MSSQL · Entity Framework · Microsoft Azure · jQuery

Padma was an in-house platform and was never released publicly, so there's no live demo. This page describes the design, not code or client data.

The problem

Genuine Technology builds HR, payroll, accounts and ERP systems for many clients, and each one wants its own forms, fields and reports. Building every screen by hand meant the same work over and over: a table, a form to fill it, a list to browse it, an export, a report.

Padma's goal was to let the team, and eventually clients, build those screens in a visual designer instead, and have the platform take care of the database, the data binding and the rendering.

Constraints

  • Real business data. A designed form wasn't a mock-up: it had to store, validate and relate real records, including master and detail entries.
  • Many organizations. Each business using Padma needed its own apps and data, kept apart from everyone else's.
  • Change without redeploys. Adding a field or a page had to take effect without shipping new code.
  • Data outside the app. Pages and data had to be usable from other websites and systems, not only inside Padma.

Six design decisions

1 Pages saved as data, rendered at runtime

Problem. Generating code for every designed page would mean a build and a deploy for every change.

Choice. The Studio saves each page as a structured definition: its components, their position, captions, fields and data bindings. A separate client app reads that definition and builds the forms, tables and dashboards on the fly, so a saved change shows up on the next page load. Saved designs can be reopened in an edit mode and changed later.

Trade-off. The renderer does more work on each page load, and bugs are harder to trace because the page only exists at runtime. In exchange, nobody needs a developer to add a field.

2 Forms that build their own tables

Problem. A no-code form is useless if a developer still has to create the table behind it.

Choice. An entity builder turns the fields on a form into database tables and columns, creating new ones on first save and altering them when the design changes. Users can also bind a form to a table that already exists. The platform records how tables relate, so a master-detail form can follow those links, even several levels deep, and save the parent and its child rows together.

Trade-off. The schema follows the designer, so renaming or removing fields on a table with live data needs care. We accepted that to make "draw a form, get a working table" possible.

3 One save, all or nothing

Problem. A save touches three places: the registry of apps, modules and pages, the database tables, and the page definition. If one fails halfway, the page breaks.

Choice. All three steps run inside one transaction. The page definition is written last, and the transaction commits only after that write succeeds; any failure rolls the whole save back.

Trade-off. A failed save means starting again, but there are no half-saved pages pointing at tables that don't exist.

4 Each organization gets its own space

Problem. Many businesses build apps on the same platform, and their tables and data must never mix.

Choice. Each organization gets a unique key when it signs up. Its tables, its record of table relationships and its apps are all scoped to that key, and every lookup in the Studio only shows that organization's tables.

Trade-off. The platform enforces the separation, not separate databases. It's cheaper to run and simpler to back up, but the code has to get the scoping right everywhere.

5 Components bind to data, not just display it

Problem. Business screens are more than text boxes: they need dropdowns filled from other tables, calculated values, filtered lists and charts.

Choice. Data handlers and data binders let each component pick its source: a table, a related table or a saved query. Dropdowns fill from other tables or a manual list, table columns can be computed, lists can be filtered by criteria, and dashboards place charts on a grid, each fed by its own query. A flexible content area lets designers mix free-form content with these components on one page.

Trade-off. Letting designers write queries is powerful but needs trust and review; it suits an in-house team better than anonymous end users.

6 Pages and data that reach beyond the app

Problem. Clients wanted Padma forms on their own websites, and other systems needed to read and write Padma data.

Choice. Any page can get an embed link with its own unguessable ID and a stripped-down layout, ready to drop into another site. An API builder maps an endpoint name to a table or saved query and serves it for reading, adding, updating and deleting records. Surveys get public links and accept file uploads, and any table can be exported to CSV or Excel or filled from an uploaded file, with the headers checked against the table first.

Trade-off. Every way in is another thing to secure and keep working, but it meant Padma data didn't stay locked inside Padma.

Results

Padma stayed an in-house platform and was never released publicly. Inside the company it let the team design data-backed forms, master-detail entries, reports, dashboards and surveys without hand-writing each screen. I built core components of it, including data handlers, data binders, entity builders, chart components, the flexible content area and embedding, and I trained in-house developers to build on the platform.

What I'd do next

  • Run every generated query through parameters and a strict allowlist, and add tests for the query builder.
  • Version page definitions, so a design change can be previewed, migrated and rolled back.
  • Put generated APIs and embeds behind proper API keys, scopes and rate limits.
  • Show a preview of the database change before a schema-altering save goes through.
